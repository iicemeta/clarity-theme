## 稳定 / 冻结

在里程碑 1 进行期间，以下契约不应被重新设计：

- 五个包导出入口，以及包导出与 Layer 运行时契约之间的区分。
- 使用方文件模型：`clarity.config.ts`、`content.config.ts`、可选 `feeds.ts` 与仅 UI 的可选 `app/app.config.ts`。
- `clarity.config.ts` 输入形态与严格的未知字段拒绝。
- Content 集合工厂与文章 schema 边界。
- 同路径组件覆盖行为，即使 Nuxt 会发出 `NUXT_B3011`。
- 使用方对站点内容、部署规则、密钥、重定向与包管理器补丁的持有。
- 事务式上游同步语义：未知路径阻止 apply；已适配的 include 路径冲突而非覆盖。

允许把过宽的运行时 appConfig 形态作为 v0.1 修正收窄，但不应为实现它而重新设计公共配置输入与包导出面。

## P0——必须解决

> **状态（2026-09-22）：以下四个 P0 项均已解决。** 问题描述保留为修复的审计记录，修复摘要见「已完成」。

### P0-1. 把服务端消费的配置移出客户端可见的 appConfig

**问题 / 当前行为**

`toPublicClarityConfig()` 把完整 `site`、`article`、`feed`、`stats`、`features` 与 `changelog` 分组序列化进 appConfig。服务端 handler 通过 `useClarityConfig()` 读取 feed/统计/站点值，三个 article 字段只用于构建接线。`integrations.scripts` 已被剔除，但剩余边界仍比其消费者需要的更宽。

这是架构边界缺陷与隐私面，不代表当前 schema 存储了凭据。`clarity.config.ts` 中不表示密钥式值；真正的密钥必须继续使用使用方仅服务端运行时配置。

**存在原因**

主题是从上游应用增量抽取的。在建立 Layer/包边界期间，单一共享 appConfig 读取器保留了上游行为。

**影响**

- 用户：更大的客户端 payload，以及主题实际上不打算保证的隐含隐私面。
- 使用方：`useClarityConfig()` 与生成类型暴露使用方客户端代码不需要的字段；`app/app.config.ts` 中的意外站点字段覆盖只被警告，不被拒绝。
- 上游：更紧的配置归属让未来上游变更更容易分类。

**测试**

历史 bundle 审计证明 `integrations.scripts` 已移除，但没有永久契约断言哪些非公共字段在客户端输出中缺失。

**风险 / 成本**

中等风险，因为 Nitro 打包、appConfig 类型、静态生成与公共辅助函数返回形态相互作用。中等成本。这是架构加固，不是紧急安全补丁。

**选定方向与里程碑**

- 保持 `clarity.config.ts` 输入兼容。
- 为 Atom/OPML/统计与仅构建值引入仅服务端的已解析配置源。私有 Nitro 运行时配置或虚拟服务端模块优于把现有 `#clarity/config` 别名变成新的公共导出。
- 从客户端 appConfig 移除 `feed.*`、`article.useRandomPermalink`、`article.hidePostPrefix` 与 `article.robotsNotIndex`。
- 明确处理 `stats.includePaths`：要么从中派生 `BlogStats` 使用的小型客户端展示事实，要么将其文档化为有意客户端可见。不要让它静默留在含义不清的“服务端配置”标签下。
- 尽可能把 `site.author.email` 移出客户端 appConfig，同时保留现有公共 feed/meta 输出，直到单独的可见性选项做出决定。
- 保持客户端必需的 Twikoo 与反镜像数据公开。
- 在 Nuxt 允许的范围内，把 app-config 边界警告变成确定的构建/类型边界。
- 为新拆分添加 payload 与类型断言。

实现备注：`src/modules/clarity-config`、`src/config/public.ts`、`src/config/app.ts`、`src/server/**`、`src/shared/utils/clarity.ts` 与消费者/兼容性测试装置。

### P0-2. 给功能关闭的路由一个运行时语义

**问题 / 当前行为**

`features.atom`、`features.opml` 与 `features.stats` 控制预渲染路由规则与 Atom alternate head 链接。Nitro handler 本身不检查开关。静态输出可能因此省略这些文件，而 dev/SSR 运行时仍会提供它们。

**存在原因**

首版实现满足了已测试的静态生成要求，而没有修改上游派生的服务端 handler。

**影响**

- 用户：禁用的公共功能在非静态部署中仍可被发现并提供数据。
- 使用方：`generate` 与 SSR/dev 之间部署行为不一致。
- 上游：路由守卫由主题持有，不应干扰上游 handler 内容变更。

**测试**

当前消费者 feature-off 变体断言生成文件缺失。它没有从服务器请求路由或断言 404 状态。

**风险 / 成本**

低到中等风险；低成本。主要风险是意外禁用使用方覆盖有意恢复的路由。

**选定方向与里程碑**

功能禁用必须意味着路由在静态输出中缺失**且**在 dev/SSR 中返回 404。作为 v0.1 缺陷修复在首次 npm 发布前实现；配置 API 不变。里程碑 1。

实现备注：功能状态必须能被 P0-1 的仅服务端配置源访问；`src/server/**`；feature-off 消费者与 SSR 用例。

### P0-3. 验证并修正反镜像导航

**问题 / 当前行为**

注入已实现并测试，包括黑名单与站点 URL 的 base64 编码。运行时导航未测试。源码检查还显示完整 `site.url` 字符串被解码并赋给 `location.host`；URL host setter 期望的是 host 而不是 URL。这是高置信度的正确性风险，不只是缺测试。

**存在原因**

该行为继承自上游模块。抽取测试刻意验证了脚本注入与上游默认值的移除，而没有从模拟镜像站导航。

**影响**

- 用户：启用的反镜像功能可能无法把访客带回规范主机。
- 使用方：该集成尚不能被称为发布完备。
- 上游：同样的可疑目标处理在上游存在；主题修复未来可能支持上游报告。

**测试**

当前测试只覆盖启用/禁用分支与编码脚本内容。

**风险 / 成本**

添加专项浏览器测试后风险低；成本低。可能的修正是派生并传递规范 host 而非完整 URL，同时保留 canonical link 更新。

**优先级 / 里程碑**

里程碑 1 的 P0。在真实浏览器用例从镜像式主机名行使导航之前，不要将该集成作为已验证发布。

实现备注：反镜像模块/客户端与兼容性浏览器装置。

### P0-4. 移除或显式迁移 no-op 的 `useRandomPermalink` 契约

**问题 / 当前行为**

schema 接受 `article.useRandomPermalink`，但主题不生成稳定固定链接。它只是外部构建脚手架的提示。

**存在原因**

转换上游博客配置契约时保留了这个字段。

**影响**

- 用户：公共开关看起来承诺了主题不持有的行为。
- 使用方：未来脚手架工具可能依赖意外暴露的 no-op 字段。
- 上游：稳定的随机固定链接生成需要持久化的消费者/站点脚手架，而非通用 Layer 渲染。

**测试**

feature-off 消费者变体只证明 schema 接受与构建兼容。

**风险 / 成本**

首次 npm 发布前风险低；成本低。实现生成器风险更高且不在计划内。

**选定方向与里程碑**

首次语义化包发布前，从主题公共配置 API 移除该 no-op，或把它移入显式文档化的消费者脚手架扩展命名空间。不要在主题中实现随机固定链接生成。里程碑 1。

实现备注：配置 schema/运行时双轨、配置文档、API 文档、消费者契约与 Content 测试。

## P1——下一步

> **状态（2026-09-22）：** P1-2 已验证并加回归测试；P1-6 除实际发布外完成；P1-1/P1-3/P1-4/P1-5 显式推迟到里程碑 2，并记录在 0.1.1 与 0.1.2 发布说明中。

### P1-1. 使外部 CSS/字体来源可配置

**问题 / 当前行为**

KaTeX 与 Inter 默认 `s4.zstatic.net`；JetBrains Mono/Noto Serif SC 默认 Google 的 `.cn` 字体端点。这些 Layer head 链接是固定的，普通使用方 head 追加没有提供文档化的移除或替换方式。

**存在原因**

它们是为上游站点地区优化的继承默认值。

**影响**

- 用户：可用性、隐私、CSP/供应商策略与性能取决于使用方未选择的默认值。
- 使用方：这是公共 Layer 行为，即使它当前不是 `clarity.config.ts` 字段。
- 上游：来源选择是站点/区域策略，不是通用主题渲染逻辑。

**测试**

当前渲染测试证明默认值可用；没有变体覆盖来源。

**风险 / 成本**

中等风险，因为它增加公共配置 API；中等成本。它不是正确性或密钥安全阻塞项。

**选定方向与里程碑**

添加一个文档化的资源来源配置组，带显式默认值、替换与禁用主题提供的远程链接的方式。为兼容性保留现有默认值，除非发布评审决定需要中立默认值。里程碑 2。

实现备注：配置 schema/运行时、构建模块 head 接线、架构/配置/API 文档与消费者分支测试。

### P1-2. 修正多模式统计选择

**问题 / 当前行为**

`stats.includePaths` 在一个查询组内通过重复 `where()` 调用归约。查询组语义使这些条件为合取。因此，`posts/%` 与 `notes/%` 等多个模式会选择同时匹配两者的行（通常不可能），而不是预期的并集。

**存在原因**

当前自动化夹具只使用一个模式，未暴露组合错误。

**影响**

- 用户：配置多个内容模式时统计可能错误地变空。
- 使用方：文档中的数组语义有误导性。
- 上游：这是主题服务端适配，不是继承的上游行为。

**测试**

验证了一个 `posts/%` 夹具；不存在多用例。

**风险 / 成本**

低风险；低成本。

**优先级 / 里程碑**

里程碑 1 的 P1，或紧随服务端配置拆分之后，因为它是具体的正确性缺陷，尽管默认单模式路径是正确的。

实现备注：统计 Nitro handler 与消费者兼容性夹具。

### P1-3. 补全已知上游派生路径的同步 manifest 分类

**问题 / 当前行为**

`app/stores/**`、`app/types/**` 与 `app/utils/**` 是未知的。在当前基线，stores 与通用类型/工具文件未修改；`app/types/article.ts`、`app/types/feed.ts` 与公共图片辅助边界有主题适配。

**存在原因**

最初 manifest 优先覆盖最大的直接同步区域，并刻意让意外以 unknown 阻止。

**影响**

- 用户：这些目录中未来的上游变更多余地阻止 apply。
- 使用方：无直接影响。
- 上游：安全，但每次相关漂移都需要人工分类。

**测试**

unknown 阻止本身有同步工具回归覆盖；提议的具体映射尚未体现。

**风险 / 成本**

低风险；低成本。不要削弱 unknown 安全网。

**选定分类**

- Include：`app/stores/**`、`app/types/index.ts`、`app/types/nav.ts`、`app/utils/anim.ts`。
- Transform：`app/types/article.ts`、`app/types/feed.ts`、`app/utils/img.ts`，因为它们与 Layer 导入或公共包 API 绑定。
- 主题独有的 `app/types/modal.ts` 保持未分类，或在希望防未来上游碰撞时显式 manual。
- 对真正新增/意外的路径，保持 unknown 作为最终安全机制。

**优先级 / 里程碑**

里程碑 2 的 P1，在下一次实质性上游同步之前。

### P1-4. 添加 TypeScript / MJS 一致性门槛

**问题 / 当前行为**

公共运行时 `.mjs` 文件与 TypeScript 类型/实现源是手工配对的。现有测试证明当前运行时入口存在并验证了部分行为，但没有系统性地把 schema 形态、默认值、导出名或辅助语义与 TS 源对比。

**存在原因**

不能假设 `node_modules` 内文件的原生 TypeScript 加载，因此包需要运行时 JavaScript 入口。

**影响**

- 用户：未来的 schema/辅助修改可能带着类型/运行时漂移发布。
- 使用方：包导入的校验或行为可能与生成类型不同。
- 上游：无直接上游影响。

**测试**

Tarball 引用审计、Node 冒烟与 typecheck 覆盖存在性与行为子集，不覆盖一致性。

**风险 / 成本**

作为契约检查实现则风险低；定义有意义的一致性成本中等。自动源码生成是更大的构建系统变更，不是第一步。

**选定方向与里程碑**

在考虑生成之前，为成对导出名、schema 默认值/严格性与代表性辅助输出添加确定性一致性检查。里程碑 2。

实现备注：验证/契约装置与 `src/config/`、`src/img/`、`src/remark-plugins/` 下的成对文件。

### P1-5. 缩减 `plain-shiki` 消费者补丁

**问题 / 当前行为**

差分消费者给 `plain-shiki` 打补丁，使 `::highlight(name)` 后代获得预期作用域。主题测试当前无补丁运行，并有意接受该环境差异。

**存在原因**

缺陷位于上游依赖的选择器实现；消费者补丁保留了真实博客行为。

**影响**

- 用户：精确 plain 高亮颜色在有补丁与无补丁环境间不同。
- 使用方：真实站点必须为主题持有的渲染功能维护补丁。
- 上游：小型上游依赖修复或受支持的 selector 配置优于 fork。

**测试**

渲染已验证，但精确的有补丁 plain 高亮作用域不是当前 CI 门槛。

**风险 / 成本**

中等风险，因为选择器行为同时影响两套主题；中低成本。

**选定方向与里程碑**

先评估主题侧 selector 配置，再提交/跟进上游依赖修复。不要 fork 依赖。里程碑 2。

### P1-6. 建立首个包发布工作流

**问题 / 当前行为**

包未发布，消费者必须锁定 Git commit。验证已打包真实 tarball，但没有 tag、npm publish、provenance、发布说明或发布演练工作流。

**存在原因**

发布被刻意推迟，直到抽取与验证边界稳定。

**影响**

- 用户：安装的可发现性与可复现性较低。
- 使用方：Git 依赖解析与未来向 npm 的迁移必须手工处理。
- 上游：无直接影响。

**测试**

当前 tarball 的消费者安装已验证；发布本身未验证。

**风险 / 成本**

中等风险，因为发布使 API 语义具有约束力；中等成本。

**优先级 / 里程碑**

P1 发布赋能，在里程碑 3 执行，且只在 P0 工作与选定的 P1 契约变更完成后于里程碑 4 完成。

## P2——稍后

### P2-1. 增量的交互、无障碍、响应式与失败测试

当前实现不应仅因某个交互缺少自动化就被标记为不完整。精确缺口：

- 已实现并部分验证：归档控件、代码折叠/复制、小部件组合、预览入口、响应式抽屉/遮罩、自定义错误 UI。
- 已实现但未测试：Twikoo 远程初始化/UI、ABC 音频、搜索键盘行为/排序、图片服务失败。
- 上游 UI 已实现但无 viewport 自动化：响应式布局。

围绕真实失败模式增量添加；不要因宽泛的 UI 覆盖扩张阻塞里程碑 1。

### P2-2. 缩减可接受的警告类别

套件有意容忍 `NUXT_B3011`、链接检查器/资源噪音、Vue slot/readonly 警告、空/过小 og:image、废弃的 `twitter:card` 与远程 Shiki 资源。组件覆盖功能本身正确。只在边界修复之后调查警告类别；不要宽泛地隐藏有用诊断。

### P2-3. 支持受限/离线 Shiki 构建

远程 `esm.sh` engine 导入在受限网络可能失败。调查打包或显式本地 engine 选项。这是依赖加固，不是当前渲染缺陷。

### P2-4. 决定作者 email 可见性

`site.author.email` 是可选的，被文档化为公共 feed/OPML/作者元数据，当前进入 appConfig。P0-1 移除不必要的客户端序列化之后，再决定可见性/输出选项是否合理。没有具体的反垃圾/隐私需求时不要添加新功能。

### P2-5. 泛化纯度检查

当前校验器使用显式的上游标识允许/阻止列表与按路径的历史审计白名单。manifest 驱动或更宽的泄漏分类可减少盲点，但显式规则也让调查具有确定性。在不削弱当前保证的前提下增量改进。

### P2-6. 仅在需要时拆分大型验证装置

消费者与兼容性脚本很长，但确定、有序且是发布信心的核心。只有当 P0/P1 变更使其难以维护时才重构报告模块；覆盖与失败清晰度不得下降。

## 延后

### Deferred-1. 差分消费者重设计

外部 `theme-based-blog-v3` 环境是有价值的历史证据，但不在 Git 中、不是 CI 门槛，其 tarball/输出早于当前 HEAD。选项：

| 选项 | 判定 |
| --- | --- |
| A. 历史手工工具 | 现在保留，明确标记为非权威。成本最低并保留该环境。 |
| B. 加入本仓库 | 拒绝：它会把上游文章/私有站点数据混入主题包并削弱纯度边界。 |
| C. 独立私有仓库/模板 | 如果差分测试继续发现边界情况，这是优先的最终设计。为其 manifest、补丁、内容源、工作流与主题引用做版本管理。 |
| D. 删除 | 现在拒绝：它仍提供合成夹具无法提供的真实内容洞察。未来任何删除前先归档。 |

延后到里程碑 2 之后。只有当特定内容兼容变更需要时才手工重跑；绝不将其持久化输出引用为当前验证。

### Deferred-2. Node 26 CI 覆盖

`>=26` 是开放的 engine 分支，没有稳定的固定 CI 代表。当声明固定的受支持 Node 26 范围时再添加矩阵分支。不要仅因为 CI 今天无法代表它而移除开放 engine 分支。

### Deferred-3. 宽泛视觉回归 / 新平台工作

视觉回归系统、CMS、数据库层与通用 i18n 框架仍在当前产品边界之外。只在发布维护证明具体需求后重新审视。

## 不修复

- **在主题中实现随机固定链接生成。** 稳定的生成固定链接需要消费者持久化/脚手架，不是通用 Layer 渲染行为。
- **携带使用方包管理器补丁。** Pnpm 补丁不随 npm 包传递，且依赖消费者内容/部署选择。
- **运营第三方服务。** Twikoo、统计分析、搜索索引、图片代理、评论后端与 CDN 仍是集成，不是主题托管的服务。
- **自动合并上游变更。** 同步保持建议性、事务性与人工审查。
- **把完整差分博客移入本仓库。** 见 Deferred-1。
- **保证 `clarity.config.ts` 或 appConfig 可以存储密钥。** 真正的凭据属于使用方仅服务端运行时配置。

## 重复 / 误报分诊

- 服务端安全配置、路由守卫、CDN 默认值、差分状态、同步分类与双轨漂移此前在多个旧状态章节中重复列出。现各自合并到一个 ID 下。
- “自动化测试无补丁运行”本身不是缺陷：无补丁路径是正确的默认主题 CI。真正的债务是陈旧的差分环境与已知依赖补丁。
- `ipx` 不是默认主题要求。它是可选的，只在 ICO 真的经过 IPX 时适用。
- 差分 workspace 中未注册的 `@vue/shared` 补丁不生效，不是主题债务。
- 同路径组件覆盖按设计工作；只有其 `NUXT_B3011` 警告噪音仍是 P2 质量问题。

## 里程碑

### 里程碑 1——核心边界与正确性加固

范围：P0-1 至 P0-4，加上服务端配置拆分触及统计行为时的 P1-2。

理由：在增加更多 API 面之前，解决公共语义、路由行为与高置信度正确性缺陷。该里程碑不得重新设计 UI 或包导出模型。

退出标准：服务端/客户端配置边界有断言；feature-off 路由返回 404 且从静态输出消失；反镜像导航在真实浏览器行使；no-op 固定链接契约被移除或显式迁移；多模式统计被测试；完整有序验证套件通过。

**状态：完成（2026-09-22）。**

### 里程碑 2——兼容性与质量细化

范围：P1-1、P1-3、P1-4、P1-5，以及这些变更引入的针对性测试。

理由：这些变更改善消费者兼容性与可维护性，不阻塞正确性工作。资源来源配置与 manifest 分类都影响公共或同步契约，值得单独评审。

退出标准：远程资源来源可配置；已知路径分类显式；TS/MJS 一致性门槛通过；plain-shiki 方向已验证；上游同步保持最新或记录已审查差量。

### 里程碑 3——发布候选加固

范围：P1-6、最终文档同步、完整发布演练，以及减少用户可见警告噪音或安装风险的针对性 P2 清理。

理由：在发布前冻结 API 行为，并通过现有分层管线验证确切发布 commit。

退出标准：满足上文发布就绪清单，除实际 npm 发布之外。

**状态：完成（2026-09-22）**——发布门禁、发布工作流、发布文档、更新日志与 registry 消费者测试已实现；工作流本身需从打了 tag 的 GitHub Release 触发运行。

### 里程碑 4——发布与维护

范围：打 tag 并发布首个包版本，把文档从 Git 锁定语言迁移到已发布包范围，监控安装/CI，并开始增量 P2 覆盖。

理由：发布是维护步骤，不能替代里程碑 1 的正确性工作。发布后，语义化版本与上游漂移维护成为主导约束。

**状态：Theme 发布已完成**——`clarity-theme@0.1.2` 已发布。后续维护 SemVer、registry 监控与发布后消费者检查；首个 `create-clarity-theme` 发布是创建包剩余的人工操作。
